# 21. Training-recipe knobs — the config surface we never varied

**Scope.** Every training/inference config knob we have never swept, why each is (or is not) worth an
arm, the hardware ceiling that decides which are even runnable, and the OFAT screen results.
Narrative: `PROGRESS.md` 2026-07-30/31. Related: `20.ReasoningCoT_Stats.md` (the `enable_thinking`
artifact), `14.Flagship2048_Stats.md` (the deployed recipe), `11.Backbone_Bakeoff_Stats.md` (resolution
— the *only* knob ever swept before this).

**Origin.** Taha's observation that every adapter we have ever trained used the *same* recipe (QLoRA
r8, seed 1337, 3 epochs, lr 2e-4), and that the only knob we ever varied was image resolution — which
happened to be our single biggest win. Two prior wins (`do_sample`, the empty `<think>` channel) came
from *config defaults nobody set*, so the question was whether more of those exist.

## §1 — Config audit: 4 clean negatives, 1 positive (2026-07-30, 0 GPU)

Hunting for more `do_sample`-class artifacts. **The inference-side surface came back clean** — this is
a useful negative in itself: that class of bug is now exhausted there.

| candidate | verdict | evidence |
|---|---|---|
| `repetition_penalty` in vendor `generation_config.json` | **negative — inert** | It is **1.0**. Would have applied *even under greedy* (unlike temperature) and would have suppressed repeated tokens in comma-separated multi-label answers. It doesn't. |
| `cutoff_len: 8192` vs 2048² sequences | **negative — not biting** | 2048² = 4,194,304 px ÷ (patch 16 × merge 2 = 1024 px/token) = **4,096 visual tokens**; every deck is built `--max_images 1` (and `--apply_policy` forces K=1 at `export_sharegpt.py:232`) ⇒ ~4,300 tokens total, well under 8192. ⚠️ LF's *default* is 2048 — if that override is ever dropped, the answer is silently truncated off every row. |
| train↔infer image resize | **negative — faithful** | `_cap_pixels` (`inference.py:153`) and LF `_preprocess_image` (`mm_plugin.py:237`) are the same sqrt-ratio downscale with the same default PIL filter; only `int()` vs `round()` differs (≤1 px), erased by the processor's 32-multiple rounding. |
| `enable_thinking` (still unset → `True`) | **real but ≈0 value** | Root-caused in `20 §0`. Direct cost ~5 constant tokens of loss/row; the measured damage was a *scoring* artifact, already fixed. **Hygiene, not a lever** — and changing it would add a second variable to the all-data retrain. |
| **`freeze_vision_tower` / `freeze_multi_modal_projector`** | **★ POSITIVE** | Both default **`True`** (`finetuning_args.py:484-490`), **neither is set in any YAML, script, or CLI override.** ⇒ `lora_target: all` has only ever meant *all linear layers of the language model*. **All 36 adapters have a frozen ViT and a frozen projector.** |

**⚠️ PARTIAL CORRECTION (verified 2026-07-31 from the deployed adapter's own weights).** "The vision
pathway has never received a gradient" is **too strong**. `cls_rebal_2048_s1337/checkpoint-11000`
`adapter_config.json` has `target_modules` including `{0,1,2}.linear_fc{1,2}`, and the safetensors hold
**12 vision tensors** — all of them `visual.deepstack_merger_list.{0,1,2}.linear_fc{1,2}`. So:
- **ViT encoder blocks: genuinely frozen** (no `visual.blocks.*` tensors) — the original claim holds here.
- **DeepStack merger / projector heads: ARE trained** — `freeze_multi_modal_projector=True` did *not*
  exclude them (LF's exclusion presumably keys on a differently-named projector module).
⇒ the model can already re-weight **how** multi-level visual features are fused; what it cannot change
is **the features themselves**. This weakens (but does not kill) the unfreeze arm's motivation.

**Why the positive matters.** `16 §2d` found one mechanism behind the worst slice of four tasks —
*"when the model cannot resolve the image it falls back to the prior… our metrics partly measure
base-rate exploitation, not perception."* That is a perception failure, and we have been fine-tuning
the language model exclusively. `9`/[[project_qwenvlconnector]] separately showed the fused visual
features are load-bearing (detection −0.55 with DeepStack off) — features that have never received a
gradient. Counter-consideration: it is a natural-image ViT adapting to medical data on 41k rows,
with real destabilisation risk.

**★ A latent interaction worth recording:** resolution is our best-proven lever, and the obvious next
step is blocked by `cutoff_len`. **3072² = 9,216 visual tokens > 8192** ⇒ LF would truncate the answer
off every row and log nothing. Any further resolution push *must* raise `cutoff_len` in the same change.

## §2 — ★ The hardware ceiling (this decides which arms exist)

> ⚠️ **PARTIALLY SUPERSEDED by §3a (2026-08-01).** The OOMs below are real, but they were
> **allocator fragmentation, not a hardware ceiling**. With
> `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`, **2048² training RUNS** (18,863 MiB, ~5.7 GB
> headroom, 0 OOM) — it is merely **5.2× slower** than 768². Read §3a before citing anything here.

**The deployed recipe cannot run on our only hardware.** First-ever LF training run on `ws`
(2026-07-30) died at step 0/3033:

```
torch.cuda.OutOfMemoryError: CUDA out of memory. Tried to allocate 4.86 GiB
  in ForCausalLMLoss -> fixed_cross_entropy
```

**Mechanism:** the CE loss materialises a logits tensor of `batch × seq × vocab × 4 B`
= `2 × ~4,300 × 151,936 × 4` ≈ **5 GB in one allocation**, on top of weights + activations. flare's
A100 40/80 GB absorbed it; a 24,564 MiB A5000 does not.

**Fix:** `bsz 1 / grad_accum 8` — effective batch stays 8 and the gradient is the mean over the same
8 samples, so it is **mathematically near-equivalent** (a safe deviation, unlike touching LR or epochs).
Committed as the launcher default in `34ac9d8`.

**⚠️ Gradient checkpointing is ALREADY ON** — the recorded `gradient_checkpointing=False` is the unused
HF flag; LF enables it on the model directly (`model/model_utils/checkpointing.py:164-166`, with
`disable_gradient_checkpointing` defaulting False). ⇒ **it is not an additional memory lever**, and the
2026-07-16 reference of **22.7 GB peak at bsz1/2048²** was already the checkpointed figure ⇒ **~1.3 GB
of headroom on a 24 GB card.**

**Consequences for the arm list:**

| arm | feasible on 24 GB? | why |
|---|---|---|
| rank 32, effective batch, LoRA+, rsLoRA, LR, epochs, dropout/NEFTune | ✅ | ~zero extra memory (accumulation is free; LoRA params are tiny) |
| **8-bit** | ❌ likely | ~+4 GB of weights vs 4-bit. Also the *least* interesting precision point — bnb int8 training is slower than NF4 and QLoRA reports NF4 ≥ int8 quality-per-byte. |
| **bf16 (no quantization)** | ❌ | ~+11 GB of weights. The real prize on this axis, and the most expensive. |
| **3072²** | ❌ | 4,096 → 9,216 tokens scales both the logits tensor and activations (and needs `cutoff_len` raised, §1). |
| **unfreeze ViT + projector** | ⚠️ marginal | adds ViT backward activations on top of ~1.3 GB headroom |

**The one lever that would unlock the memory-bound arms is NOT available as a config flag:** Liger's
fused linear+cross-entropy targets exactly the 4.86 GiB allocation, but LF's dispatch
(`model/model_utils/liger_kernel.py`) covers `qwen2_vl`, `qwen2_5_vl`, `qwen3`, `qwen3_moe` — **not
`qwen3_vl`** — and the package is not installed. Wiring it is a code change to the training path.
Alternatives: DeepSpeed ZeRO-3 sharding across all 4 cards (config-only, but consumes the whole box
for one arm), or a ~30-line chunked-CE patch.

## §3 — The OFAT screen (design)

**One knob per arm; everything else frozen** to the deployed cls recipe. Driver:
`scripts/run_recipe_screen.sh` (`f6f71df`) — one card runs a *chain* of arms, each
`train → assert → eval → assert → append row`. All arms share ONE training deck (built + tokenised
once). Runs in `flare-qwen3-train`, never the Docker-pinned inference env.

**Scale:** train `A_prime` → eval `B_prime` (the 30% quick subsets), cls only, 2048² matched,
**per-dataset macro balanced accuracy** ([[project-per-dataset-not-pooled-metric]]).
**Confirmation** for the top 1–2 only: full A → full B, **both directions**, plus a second seed and a
multi-label check.

**Why staged rather than cross-validating every arm:** single-direction results have burned this
project ≥3 times — the +0.045 early-layer detection "win" reversed under cross-validation (`9`), CoT on
detection sign-flipped between directions (0.580 A→B / 0.549 B→A, correctly called noise, `4 §1`), and
Alex's task token won on V1 splits and did not transfer.

**Decision rule: |Δ macro BA| < 0.01 is UNRESOLVED, not a result** (≈ our observed noise floor).

| arm | knob | prior |
|---|---|---|
| `base` | — (anchor at bsz1/ga8) | mandatory; A′-scale is not comparable to the flagship's 0.748 |
| `rank32` | `lora_rank 32, lora_alpha 64` | **highest** — r8 is last year's InternVL number carrying 41k rows × 6 tasks on an 8B; practice is 16–64; nearly free |
| `batch32` | `gradient_accumulation_steps 32` | eff. batch 8 is small/noisy at 2048²; zero extra memory |
| `loraplus` | `loraplus_lr_ratio 16` | supported, unused; commonly pays |
| `lr1e4` | `learning_rate 1e-4` | coupled to rank — interpret after `rank32` |
| `ep4` | `num_train_epochs 4` | never varied; matters most on oversampled decks (k2a, reg×3) |
| `reg` | `lora_dropout 0.05, neftune_noise_alpha 5` | both off; same oversampling argument, weaker |
| `rslora32` | `rank 32 + use_rslora` | only meaningful at raised rank ⇒ paired on the same card as `rank32` |

**Not in the screen, no training needed:** the periapical compound-label exploit (`16 §2c`, free, and
multi-label is periapical-only on the test set) and `num_beams` (never set → 1; runtime slack allows
exactly 2; helps long structured outputs, useless for 1-token cls).

### §3a — Probe + the two measurements that reshaped the whole plan

**Probe 1 (2048², no allocator flag): FAILED.** OOM at bsz1 — `Tried to allocate 8.32 GiB` in the
**backward** pass, peak 18,385 MiB of 24,564. Combined with the earlier bsz2 failure this produced the
(wrong) conclusion that 2048² training was impossible on `ws`.

**★★ THE ALLOCATOR FINDING (2026-08-01) — worth ~13 GB, discovered by accident.** The `rank32` cls arm
was running at **23,204 MiB and 15.56 s/it** (vs ~10.2 GB / 7.1 s/it on every other card), with step
time *rising*. Trainable params were the expected 89.0M (4× base's 22.3M), which accounts for ~1 GB —
not 13. Diagnosis: **caching-allocator thrash near the ceiling**. Relaunched with
`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`:

| | before | after |
|---|---|---|
| memory | 23,204 MiB | **10,247 MiB** |
| speed | 15.56 s/it | **7.23 s/it** |

**⇒ set `expandable_segments:True` before concluding ANYTHING is memory-bound.** It nearly cost us a
wrong verdict about our own hardware.

**Probe 2 (2048² WITH the flag): ✅ 2048² TRAINING WORKS.** Ran clean to step 6/50, **18,863 MiB used,
~5.7 GB headroom, zero OOM**. So §2's "the deployed recipe cannot run on our hardware" was
**fragmentation, not a hardware ceiling**.

**But 2048² is ~5.2× slower than 768²: 38.5 s/it vs 7.4 s/it.** Consequences:
- **A full all-data cls retrain at 2048² ≈ 13,946 steps × ~38.5 s ≈ 6 days on one card** (4–6 solo).
  This is now the single dominant item on the schedule.
- **Screening at 2048² is impossible** — one A′ arm would take ~37 h. 768² is the screening resolution;
  2048² is for the final build only.
- 3072² remains out (activations roughly double again, and `cutoff_len` would have to rise, §1).

**Measured screening cost at 768²:** ~7.2 s/it, ~10.2 GB, **3,507 optimiser steps per normal cls arm
≈ 7 h**; ML arms are ~**1.2 h** (958-row deck → 369 steps). ⇒ **ML experiments are ~6× cheaper than cls.**

#### ★★ The unifying mechanism: the three catastrophic arms NEVER CONVERGED

Not overfitting — **underfitting**. Baseline drives train loss to **0.0006** (it memorises A′), and
every arm that reached ~0.00x landed within ±0.05 on eval. The three disasters are exactly the three
whose train loss stayed 10–200× high:

| arm | train loss | eval Δ | what it changes |
|---|---|---|---|
| rslora32 | 0.0655 | −0.113 | scaling α/√r = **11.3** vs α/r = 2.0 (**5.7× hotter**) |
| loraplus | 0.1282 | −0.260 | B-matrix LR = 16 × 2e-4 = **3.2e-3** |
| rank64 | 0.1318 | −0.293 | 178M params at lr 2e-4 (8× more rank-1 terms per step) |

**All three raise the effective update magnitude ⇒ the optimiser oscillates instead of descending.**
**This recipe sits right at the edge of stability at lr 2e-4.** More data would NOT fix any of them;
a colder LR does — proven by `rank64_lr1e4`: **loss 0.1318 → 0.0025, eval 0.3036 → 0.5975 (+0.294).**

**⚠️ "rank saturates at 32" is NOT established.** `rank64_lr1e4` moved rank **and** LR together. The
LR-halving penalty measured independently at r8 is **−0.0202** (base 0.5964 → lr1e4 0.5762). Adding it
back: `0.5975 + 0.0202 ≈ 0.6177` ≈ rank32's **0.6185** — indistinguishable. r64 has **never** been
tested at r32's LR. The clean test is `rank64_warm` (r64 @ 2e-4, warmup 0.03 → 0.10), **written and
pushed but never successfully run** (killed in a card collision).

**Also corrected:** the earlier reading that regularisers losing proves we are "under-capacity" was
**wrong** — baseline fits A′ to 0.0006, so nothing is capacity-*starved*. rank32 wins on
**generalisation at equal fit**, an optimisation-geometry effect, not a capacity shortage.

#### `nothink` — ⚠️ INVALID, DO NOT CITE (superseded by `nothink_tmpl`, §3e)

**This arm is confounded and its null result must not be trusted.** `enable_thinking=false` does NOT
remove the empty `<think></think>` block — `template.py:418-426` adds it *either way* and the flag only
moves it from the loss-computed **target** (`true`) to the **prompt** (`false`). Our inference path
(`vlm_prompt.build_chatml`) never emits think tags in the prompt, so `enable_thinking=false` trained the
model with the block pre-filled into its context and then evaluated it *without* → a **train/infer
mismatch**, not an ablation of the reasoning channel. The sign-flip below (A′→B′ +0.0088, B′→A′ −0.0265,
5/10 dataset consistency) is the signature of that mismatch, not of a null effect. **The real ablation is
`qwen3_vl_nothink` (§3e), which removes the tokens entirely and IS prompt-consistent with inference.**

**★ Direct evidence of the artifact, from the label dump.** Base arm's supervised target tokens:
`151667, 271, 151668, 271, 32, 151645, 198` = `<think>`, blank, `</think>`, blank, **`"A"`**,
`<|im_end|>`, newline. **The answer is ONE token, preceded by FOUR tokens of empty thought block.** So on
a cls row the loss-computed target is 4 tokens of constant boilerplate + 1 token of answer. It still
costs nothing measurable, because constant tokens saturate immediately and their gradients vanish.

**Also observed (bears on `20 §0`'s open question):** ML emits `</think>` on **981/981** predictions
while cls emits it on **0%**, from identical training. The asymmetry is real and reproducible.
The metric is safe — `evaluation/evaluation.py:177` strips `</?think>` — so the `+THINK` guard flags
raw text only; **ML macros are NOT contaminated**.

**`chestdr` has ≈0 test rows** (`19 §2`) — so read periapical, not the macro.

**★ LADDER COMPLETE (2026-08-02 05:15) — base < 32 < 64 ≫ 128. rank64 is the ML optimum, both directions.**

- **rank32 replicates on ML in BOTH directions**, +0.040 / +0.034 on periapical, and the gain is
  **entirely on the scored dataset** — chestdr is flat (+0.001 / −0.007). This is the OPPOSITE of cls,
  where the gain landed on zero-weight datasets.
- **★★ rank64 is the ML optimum, now confirmed in BOTH directions** — periapical **+0.052 / +0.061** over
  base and **+0.012 / +0.027** over rank32. Direction spread is **0.5389 vs 0.5350 = 0.0039**, barely above
  the 0.0031 noise floor below ⇒ this is a stable effect, not a lucky direction. It **CONVERGED** (ML's loss
  floor is ~0.20 for long label-set targets, so 0.21–0.22 vs base 0.208 is normal — *not* the cls divergence
  of 0.1318 vs 0.0006). ⇒ **ML's capacity optimum is 64, cls's is 32.** Plausible mechanism: emitting a
  *set* of labels with per-label evidence needs far more distinct output behaviours than a 1-token class.
- **★ rank128 COLLAPSES — and by a DIFFERENT mechanism than the cls catastrophes.** macro 0.3809, with the
  damage concentrated on **chestdr (0.4269 → 0.2439, −0.183)** while periapical only falls to 0.5179.
  Critically, **its final loss (0.2325) is indistinguishable from rank64's (0.2121)** — so unlike
  `rslora32`/`loraplus`/`rank64@2e-4` (§3b, losses 0.065–0.132 against a 0.0006 baseline), rank128 **fit the
  training data fine and still lost 0.15 macro held-out**. Equal fit + much worse generalisation =
  **genuine over-parameterisation**, not a stability failure. At **981 training rows**, 356 M trainable
  params (≈363 k params per training example) is past the useful capacity.
- ⇒ **two distinct failure modes are now on the board:** *non-convergence* (any knob that raises the
  effective update magnitude at lr 2e-4 — diagnosed by a high train loss) and *over-parameterisation*
  (diagnosed by a normal train loss with a collapsed eval). Read the train loss first; it separates them.

**★ Empirical noise floor, from an accidental duplicate:** two `base_ml_B2A` runs at identical config
and seed gave **0.5087 vs 0.5056 = 0.0031 spread** (GPU nondeterminism under 4-bit). So ML macro deltas
of +0.013/+0.029 are 4–9× noise, and the periapical deltas far more.
*(Provenance note: the duplicate came from `screen_ml_base_B2A.log`, matching a command reported
REJECTED and never executed. Unexplained; scientifically harmless.)*

| change | measured Δ | ≈ Δ overall |
|---|---|---|
| rank32 on cls | +0.009 BA (test-weighted) | **+0.003** |

| **rank64 on ML** | **+0.052…0.061 F1 (periapical, BOTH directions)** | **≈ +0.017…0.020** |

### §3d — ★★ The α (LoRA-scaling) axis — CLOSED 2026-08-02. `α = 2r` is at a SHARP OPTIMUM.

**Why this axis existed at all.** LoRA applies `W + (α/r)·B·A`; the ratio **`s = α/r`** is a plain scalar
that sets how loudly the learned correction speaks. **All 22 arms above pinned `α = 2r`**, inherited from
last year's InternVL config and never questioned — so **`s` was CONSTANT at 2.0 across the entire screen**,
for baseline and every rank arm alike. That was good hygiene for the rank question (capacity varied at
fixed scaling ⇒ unconfounded) but left scaling completely unmeasured. `rsLoRA` showed the axis is worth
**±0.11** (it lost 0.1126 purely by moving `s` 2.0 → `α/√r` = 11.3), so it was high-sensitivity *and* blank.

**Design.** Fix rank at each task's own optimum (cls r32, ML r64) — perturb the config we would actually
ship — and move only α, one step cooler and one step hotter. ML run in **both directions**; cls A′→B′ only
(7 h/arm vs ML's 1.2 h). Everything else frozen, 768², seed 1337, `pix=589824`.

**MULTI-LABEL (r = 64 fixed).** Reference row = `rank64` from §3b.

#### What this establishes

- **★ `α = 2r` is a genuine PEAK, not the safe end of a slope.** Both sides lose, on both tasks, in both
  ML directions. The inherited convention — never chosen deliberately by us — sits at the optimum.
- **★ The peak is SHARP.** On cls, moving `s` by ±1.0 costs **0.064 (cooler) / 0.130 (hotter)** — an order
  of magnitude more than the entire rank win (+0.0221). This axis had far more *potential* than rank; it
  simply happened to already be maximised.
- **★ Asymmetric, and it retroactively explains rsLoRA quantitatively.** Hotter hurts ~2× worse than
  cooler (cls −0.130 vs −0.064; ML −0.100 vs −0.017). Extrapolating that monotone degradation to
  rsLoRA's `s = 11.3` lands squarely on its measured −0.1126 ⇒ **rsLoRA was never a special failure mode,
  just this same curve sampled far out.** One less unexplained arm.
- **★ The two sides fail for DIFFERENT reasons, exactly as §3b's train-loss rule predicts.** α=96 diverges
  (loss 0.0150 vs 0.0006 = the hot signature, same family as rslora32 / loraplus / rank64@2e-4); α=32
  converges fine (0.0034) and merely generalises worse. **The rule has now been used predictively, not
  just retrospectively.**
- **ML's α=192 damage lands on the scored slice:** periapical 0.647 → 0.488. Consistent with everything
  else in §3b — periapical is where every ML capacity/scaling effect actually shows up.
- ⚠️ **A prior was falsified, worth recording.** Going in, the stated prior was *"α=32 (cooler) is likelier
  to win, since everything that broke this session broke by getting hotter."* **Wrong** — cooler loses too.
  The correct reading of the earlier failures was *"the recipe sits at an optimum in scaling and every
  broken arm moved away from it,"* not *"the recipe is too hot."*

#### Adoption: NOTHING. The axis is closed.

Keep `α = 2r` everywhere ⇒ **cls r32/α64, ML r64/α128** stand unchanged. Do not revisit α without a
change of rank, LR, or data scale — those are the things that could move the peak.

**⇒ SCREEN COMPLETE: 26 arms, exactly ONE real win (rank).** Every other knob — LR, epochs, effective
batch, regularisers, rsLoRA, LoRA+, warmup, the thinking channel, and now α — is at or near its optimum
on the deployed recipe. That is a much stronger statement than "unexamined," and it is the finding to
report in the paper: the inherited recipe was *right*, and we now know by how much on each axis.

### §3e — ★ The empty reasoning channel: the RIGHT ablation. Keeping it HELPS both tasks. (2026-08-02)

Replaces the confounded `nothink` arm. New arm `nothink_tmpl` → `template=qwen3_vl_nothink`, which removes
the `<think></think>` tokens **entirely** (target AND prompt) — the two `register_template` calls are

**★ Removing the tokens HURTS in all four cells** (cls dir-avg −0.0085 vs a 0.005 floor; ML −0.0226 vs a
0.0031 floor). Both directions negative on both tasks ⇒ the empty reasoning channel is **load-bearing, not
inert**. This directly overturns `20 §0`'s "it's a harmless artifact" and the `nothink` null above.
**KEEP `enable_thinking` at its default.**

**★★ The two tasks help by DIFFERENT mechanisms — established by the `+THINK` guard.** cls emits `</think>`
on **0/2289** predictions, ML on **981/981** (identical training). So:

- **ML** generates the tags at inference. Periapical (the whole scored ML slice, official scorer): think-ON

- **cls** never generates the tags, yet still loses when they are removed from *training*. So the cls effect

⇒ the compute vs format-matching question is **open and the evidence is split** (ML leans compute, cls leans
format). The deciding experiment is a **filler-length sweep on ML** (0 / N / 2N filler tokens): if more
inference tokens buy more ML F1 → compute; if flat → format-matching. **NOT a config knob** — `add_thought()`

(a real confound: pause-token papers use a *learned* `<pause>` token we don't have). Scoped, not run.

**⚠️ Under-prediction lever noticed in passing:** on periapical the model predicts **2.2–2.4 labels vs a gold

point found on B′ must be confirmed on A′.

### §3f — ★★ Filler-compute probe: the empty `<think>` gain is FORMAT-MATCHING, not compute. (2026-08-03)

**Question (from §3e):** ML emits the empty block at inference and gains recall from it — is that the
tokens buying **serial compute** (pause-token effect) or just **format-matching** Qwen3's post-training
structure? If compute, padding the block with *more* generated tokens should help *more*.

**Method.** Two templates `qwen3_vl_pad_{s,l}` copy `qwen3_vl` (ReasoningTemplate, thinking on) with the
empty block padded by dummy `. ` tokens in the **loss-computed target** → the model learns to *emit* them
= N extra forward passes before its first real answer token. ML only (cls emits 0 think tokens, §3e).
Filler = `. ` because newlines collapse (128 → 4 tokens); `. ` is ~1:1. 768², both directions. Smoke
verified the filler lands in the target (16 / 64 dots), not the prompt, and `strip_think_block` removes
the whole block at eval so scored answers are clean.

**Result — an INVERTED-U with a sharp peak at the empty block:**

| think tokens | arm | A′→B′ | B′→A′ | eval s (~970 cases) | s/case |
|---|---|---|---|---|---|
| 0 | nothink_tmpl | 0.479 | 0.488 | 1090 | 1.13 |
| **4** | **base (empty)** | **0.5068** | **0.5056** | 1465 | 1.51 |
| 21 | pad_s | 0.4423 | 0.4307 | 2797 | 2.88 |
| 69 | pad_l | 0.4541 | 0.4368 | 6547 | 6.75 |

**★ Compute is DEAD.** Monotonic-up was the compute prediction; instead pad_s and pad_l are both **−0.05 to
−0.07 below** the empty block (≈20× the 0.0031 noise floor), in **both directions**, and pad_l ≈ pad_s
(69 ≈ 21) — *more* filler did not recover anything. The model gets no benefit from being forced to emit
meaningless tokens.

**★ The mechanism is FORMAT-MATCHING.** The empty `<think></think>` aligns the target with Qwen3-VL's
post-training structure; the *instant* junk goes inside the block the model is off-distribution, and the
plateau (21 ≈ 69) is the signature of "any dummy content breaks the match, quantity is secondary." This
also retro-explains cls (§3e): cls emits 0 think tokens yet still gains from the block in *training* — a
pure format/training effect, no inference compute, exactly consistent.

**★ Runtime would have killed the cheap path independently.** pad_l = **6.75 s/case**, over the ≤1.5× gate
(≈6.57 s/case, `13 §1`) on the ML slice alone. Padding was never free — inference cost scales with the
filler (1.51 → 2.88 → 6.75 s/case for 4 → 21 → 69 tokens ≈ 12–14 tok/s decode).

**⇒ Conclusions.**
- **Keep `enable_thinking` on** — the empty block is a format sweet spot (§3e), and this confirms it is a
  *peak*: both removing it (nothink) and padding it (pad_s/pad_l) are worse.
- **The cheap CoT path — pad with dummy tokens — is DEAD** (hurts, doesn't scale, runtime-heavy).
- **If reasoning can help at all, it must be MEANINGFUL per-example content** (STaR / target-side traces,
  `20 §4`), not filler. That is a real build gated on the un-run "does short reasoning help?" measurement,
  not a free win.

**Honest residual (the §3f confound, as pre-registered):** a *negative* filler result cannot fully separate
"compute doesn't scale" from "`. ` is specifically bad filler" (dots may read as trailing-off). What is
airtight: **dummy-token padding is not a usable lever.** Whether a *learned* pause token would differ is
untested and low-priority given the runtime cost.

arms `pad_s`/`pad_l` (`run_recipe_screen.sh`), commit `1806ef3`. rank-8 arm; direction clear, r64 transfer

### §3c — Process failures worth not repeating

Five self-inflicted incidents, all recoverable, all avoidable:

1. **`pkill -f <pattern>` matched the shell carrying it** → killed my own SSH session mid-command
   (exit 255), leaving an **orphaned trainer with no driver** (trains for hours, then no eval, no row).
   Happened **3×**. ⇒ **never pattern-kill on this box: list PIDs first, then `kill` by explicit PID.**
2. **`ps -u taha -o cmd | grep -q "<pattern>"` in a wait-loop self-matches forever** → the `ep2` waiter
   span for hours and never fired; a card sat idle. ⇒ use `pgrep -f` (excludes itself) or poll GPU memory.
3. **A GPU-memory waiter still races** if started in the same breath as the job it waits behind — it
   reads the card *before* that job allocates, sees it free, and fires. `rank64_warm` landed on top of
   ML rank32 (card 3 hit **22,280 MiB**, rank32 slowed 7.4 → 10.9 s/it). ⇒ confirm the card is
   **occupied** first, *then* wait for it to clear.
4. **Pre-building a deck by hand skipped its registration.** The script's `if [ ! -f "$DECK" ]` guard
   also contains the `dataset_info.json` registration, so hand-building the deck made LF unable to find
   the dataset and **both ML arms died in 6–7 s**. ⇒ let the script build it, or register separately.
5. **Two concurrent launches built the same new deck simultaneously** (B′ cls). It survived — 9,260
   lines, 0 invalid JSON — but by luck. ⇒ build once, then fan out.

6. **An env var passed via a shell variable is NOT an assignment.** `E='PYTORCH_CUDA_ALLOC_CONF=...'`
   then `... $E nohup bash ...` — bash only treats `VAR=val cmd` as an assignment when written
   **literally**; from a variable expansion it becomes a command word:
   `bash: PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True: command not found`. **All four arms died
   silently at launch**, leaving four empty logs and four idle cards. ⇒ write env prefixes literally,
   and **always verify a launch by checking resolved hyper-parameters** (param counts, α), never by
   the launch command returning cleanly.

Also fixed: the `TRAIN_FAIL` results row logged `$arm` instead of `$label`, so failed ML arms appeared
as bare `base`/`rank32` and **collided with the round-1 cls rows of the same names**.

## §5 — ML rank re-screen AT PRODUCTION SCALE (2026-08-15/16) — the missing 2048² cell

**Why.** The §3 rank screen ran at **768², A′→B′** on a WEAK base and picked ML r64/α128. When that
r64 went into the all-data 2048² build it was **FLAT on the board** ([[project-recipe-screen-overpredicts]]).
Open question (Taha): *was pushing rank a mistake, or did the screen just run at the wrong scale?* The
never-measured cell is **rank at 2048², clean held-out.** So we trained three A∪B multi-label adapters
that differ ONLY in rank and evaluated them identically.

**Setup.** Backbone Qwen3-VL-8B QLoRA 4-bit; train **A∪B** (6,415 ML rows), seed 1337, **2048²**

re-inferred greedy (its own baseline point). Sanity: 0 `</think>`, malformed empty, all 4 runs.

| rank | α | train_loss | true_test peri | true_test chestdr | **true_test macro** | valpub chestdr |

**★ Findings.**
1. **Rank was NOT a mistake — macro is monotonic r8 < r32 < r64** (0.5720 → 0.5765 → 0.5850). r64 is the

2. **But the lever is nearly TAPPED at 2048² — this is the direct confirmation of [[project-recipe-screen-overpredicts]].**

   internal periapical gain, on a board slice that is harder + distribution-shifted (board peri ≈0.475 vs
   internal 0.669), washes out to ~0.
3. **r32 vs r64 splits by dataset:** r64 wins periapical (+0.020) + macro (+0.0085); r32 wins chestdr on

4. **Distribution-shift number banked:** internal true_test periapical runs **~0.19 hot** vs the board

**Decision.** Rank is closed for ML: safe, monotonic, but ~tapped at 2048². **The road to board ML 0.51 is
